# US-07: DPDP Retention Purge + Right-to-Erasure

Status: Approved (Human Gate 1, 2026-07-24 — approved via direct /execute-story US-07 invocation, after the 6-Blocking design-gate revision). Compliance-owner sign-off items remain the open DPDP GA gate this story does not close.

## Part A — Intent

### Problem
Every prior story deferred its PII-retention obligation to a not-yet-built US-07, and the gap is now the single most-referenced GA blocker in the project: `users` (email/display_name, US-10), `visits` (visitor name/contact/host_hint/**purpose**/denial_reason, US-11), `outbox_messages` (envelope-encrypted check-in code + contact, US-11/ADR-002), and `portal_contact_verifications` (contact_value, US-13a/ADR-004) all accumulate personal data with **no purge mechanism whatsoever** — confirmed by repo-wide grep in every review pass. PRD US-07 ("DPDP auto-purge") requires: retention configurable per tenant/site; a nightly job that erases expired records; each purge writing an audit entry with count, policy, and actor; and right-to-erasure requests completed ≤72h.

### Solution
Build the retention/erasure **mechanism** (not the final legal policy — Constraint 1):
- Per-tenant, per-data-category **retention configuration** (override-with-default), so retention is "configurable per tenant."
- A **time-based purge** that, for each tenant, removes data older than that tenant's retention — **scrubbing PII in place** on referenced/skeleton-valuable tables (`users`, `visits`) and **deleting** transient ones (`outbox_messages`, `portal_contact_verifications`) — writing **one audit event per tenant** recording counts + policy + actor.
- A **right-to-erasure** command that, for a named subject (visitor contact OR staff user) within a named tenant, immediately scrubs/deletes their PII across every store the identifier reaches, writing a PII-free audit event — satisfying ≤72h by completing in seconds.
- **Structural tenant isolation** and a **`--dry-run` default** as the two core safety controls (below).

### Two Gate-1 constraints (already decided)
1. **Mechanism, not final policy.** Retention windows are legally-determined and require a named human compliance owner + real DPDP sign-off (a hard GA gate since US-10, unchanged). This story ships the mechanism with the prior stories' **placeholder windows as configurable defaults**; it does not set final legal values and does not close the DPDP sign-off gate.
2. **Human-gated prod activation.** Scrubbing/deleting visitor data is the archetypal "sensitive, irreversible operation" AGENTS.md forbids from running autonomously. This story builds/tests the mechanism **against synthetic data only** (local `vms_test`); it never runs against real data as a side effect of merge/CI. Real prod activation is a human-invoked ops action, gated like `/deploy-prod`.

### Core safety design (from the two design-gate reviews — see disposition)
- **Structural tenant isolation, not predicate-only (resolves SP-B2).** The destructive work does **NOT** run under the `BYPASSRLS` `vms_migrator` role. A new dedicated `vms_purge` role — `NOBYPASSRLS`, subject to RLS+FORCE, granted only the narrow scrub/delete privileges it needs — runs the purge/erasure. For each tenant it does `SET LOCAL app.current_tenant_id = <tenant>` inside a per-tenant transaction, so RLS's `USING`+`WITH CHECK` structurally scopes every statement to that tenant **even if a query forgets an explicit predicate** — closing the exact missing-predicate class US-13a's SF-2 hit (which was caught only because FORCE RLS was a backstop; under BYPASSRLS that backstop is gone). Enumerating the tenant list is a plain read of the tenant-global `tenants` table (no BYPASSRLS needed). Explicit `tenant_id` predicates are still written as defense-in-depth, but the GUC+FORCE is the structural guarantee.
- **`--dry-run` default (Constraint 2).** Both ops commands report what they *would* change and act only with an explicit `--execute` **plus** a typed target-tenant-slug echo confirmation and a non-prod assertion — so a fat-fingered `--execute` against the wrong DSN cannot proceed.

### Out of scope (explicit scope-creep fence)
- **Setting real/final retention values** — placeholders only (Constraint 1).
- **A compliance-manager UI/API** to edit config / submit erasure requests — the config table + ops commands are the mechanism; a management surface is a later story.
- **Per-site retention** — no `sites` table exists; retention is per-tenant, with `site` a documented future config-key extension.
- **Biometric image/template purge** — NOT APPLICABLE: no biometric store exists (US-12 deferred); named as a future data-category the mechanism can extend.
- **Redis cache purge** — NOT APPLICABLE: no Redis principal/permission cache exists (RBAC resolves from the DB every call, ADR-001 §5); Redis holds only auto-expiring rate-limit buckets, no PII. Confirmed.
- **Scheduling infrastructure** — the ops command is the artifact; wiring a real scheduler is a human-invoked deployment concern.
- **Deleting `audit_events`** — deliberately preserved (append-only, purge-exempt, holds no visitor PII per the US-11 coded-reason discipline); it is the evidence the purge is audited into.
- **Multi-contact subject unification** — `erase_subject` erases one `(channel, value)` (or one staff user) per invocation; unifying a person's multiple contacts into one request is a compliance-process concern, not built here (named, not silent).

### Risks (non-obvious failure modes)
- **A wrong cutoff scrubs/deletes live data — irreversibly.** The single highest risk. Every store needs a correct *reference timestamp* (below) and the `--dry-run` default so a human sees counts first.
- **Reference-timestamp correctness (resolves DA-B1).** The retention clock needs a real per-store timestamp, and two are missing today: `users` has no `disabled_at` and `visits` has no terminal timestamp for `CheckedOut`/`Safe`. This story **adds `users.disabled_at`** (set by the US-10 disable path — a small amendment) and uses: `users` → `disabled_at`; `visits` terminal-`Denied` → `decided_at`; `visits` non-terminal/abandoned → `created_at` (max-age, see below). `CheckedOut`/`Safe` aren't reachable yet (checkout not built); when that path lands it MUST set a terminal timestamp the purge reads — noted in ADR-005 as a forward requirement. **Never `updated_at`** (it moves on the scrub itself).
- **Coverage must reach ALL expired PII, not just the easy cases (resolves SP-B3).** (a) **Non-terminal/abandoned visits** (`Requested`/`Registered` that stall, incl. the orphaned NULL-host visits US-11's review flagged as must-cover) are scrubbed by a `created_at` max-age rule — not left forever. (b) The visits scrub column set is derived from a **verified full-column PII inventory**: `visitor_full_name, contact_value, host_hint, purpose, denial_reason, checkin_code_hash` (the initial draft missed `purpose` — a visitor free-text field). (c) The outbox purge is by **age across all statuses** (`dispatched` included — its encrypted payload holds PII+credential and is the common case), not just `pending`/`failed`.
- **Erasure must be complete across every anchor (resolves DA-B3).** A subject's `contact_value` is on `visits` and `portal_contact_verifications`; `outbox_messages` anchor to **both** visit ids (`aggregate_id`) **and** verification ids (`portal.otp.dispatch` uses `aggregate_type='portal_contact_verification'`, ADR-004 §4). Erasure deletes outbox by both sets, or an abandoned-OTP subject's encrypted contact survives.
- **Erasure vs a visitor currently on-site (resolves DA-B2).** Erasing a `CheckedIn` (on-site) or `Safe` (mustering) visitor's name would break evacuation accounting. Erasure **refuses** if the subject has a `CheckedIn`/`Safe` visit, directing the operator to complete checkout first. This is a life-safety exception DPDP recognizes; **flagged for compliance-owner confirmation** (see disposition).
- **Idempotency needs a marker (resolves DA-S1).** A scrubbed `visits`/`users` row still matches "expired" on a re-run and would re-scrub/re-count. This story adds a **`purged_at` marker** to the scrub stores; predicates carry `purged_at IS NULL`, so a second run (or a crash-resume) touches 0 rows. Deletes are naturally idempotent.
- **The audit-of-purge must never leak the erased subject (resolves SP-B1).** A bare hash of a low-entropy email/phone is brute-forceable, and `audit_events` is the one forever-store the purge can never reach — so it must not hold a recoverable contact. The erasure `subject_ref` is a **keyed HMAC** (Key-Vault key, reusing `app/crypto/hmac_hash.py`) — a stable, non-reversible reference — never a bare digest and never the raw contact. **Flagged for compliance-owner confirmation of the masking scheme.**
- **`audit_events.details` is an un-erasable PII sink (resolves DA-S3).** The append-only, purge-exempt audit table gains a nullable `details` JSONB. ADR-005 makes "**no PII in `details`, ever**" an explicit, tested contract (not just an assertion for the two new events), because anything written there is permanently un-erasable.
- **Anonymization ≠ erasure (compliance-owner call).** Scrub-in-place keeps a `visits` skeleton with `tracking_reference`/`correlation_id` and the retained audit linkage. The compliance owner must confirm the scrubbed skeleton + retained audit trail + the erasure `subject_ref` together are not a re-identification path. Surfaced, not settled.

## Part B — Contracts

### ADRs
**ADR-005 — Retention purge and right-to-erasure mechanism** (new). Triggers: new tenancy schema (`retention_policies`), retention/residency posture, and a security-posture change (irreversible destructive PII operation). Records: the **structural-isolation safety model** (dedicated `vms_purge` NOBYPASSRLS role + per-tenant GUC + FORCE RLS as the backstop; why BYPASSRLS is deliberately NOT used for destructive work); the **scrub-vs-delete decision per store** derived from a verified column inventory, and its FK/audit-linkage rationale (`users` has inbound FKs → scrub; `visits` has no inbound FK but retains audit linkage + stat value → scrub; outbox/pcv transient → delete); the **reference-timestamp source per store** + the forward requirement that a future checkout path set a `visits` terminal timestamp; the **`purged_at` idempotency marker**; the **keyed-HMAC erasure `subject_ref`** and the **no-PII-in-`details`-ever** contract; the **per-tenant** audit-event shape filling `audit_events`' NOT-NULL columns (`target_type='tenant'`, `target_id=tenant_id`, coded `reason`, fresh `correlation_id`, structured `details`); the **`--dry-run`+typed-confirmation** activation model and Constraint 1's placeholder-not-final-policy GA gate; the **NOT-APPLICABLE** dispositions (biometric/Redis/per-site); the **compliance-owner sign-off items** (final windows, erasure-on-site carve-out, masking scheme, anonymization-vs-erasure re-identification); and that the **Compliance module owns** the retention domain, pre-declaring it as an intentional cross-store writer over `users`/`visits`/`outbox_messages`/`portal_contact_verifications` (as ADR-001 pre-declared the audit sink) so `/graph-query` doesn't misread the edges.

### Statemachine impact
None. A scrubbed `visits` row keeps its terminal `status`; `visit-lifecycle.yaml` is untouched.

### Schema delta
- **New table `retention_policies`** (tenant-scoped, RLS enable+force per ADR-001): `(id, tenant_id FK+index, data_category CHECK IN ('staff_users','visits','outbox_messages','contact_verifications'), retention_seconds int NOT NULL, created_at)`, `UNIQUE(tenant_id, data_category)`. Per-tenant overrides; absence → config default. Read under the per-tenant GUC (the one legitimate RLS-scoped ops read). ADR-005 documents the category→table mapping.
- **`audit_events.details`** — new nullable JSONB. Additive; no existing caller affected. No-PII contract (above).
- **`users.disabled_at`** (nullable timestamptz) — the retention reference for staff; set by the US-10 user-disable path (amended). **`users.purged_at`** (nullable timestamptz) — scrub idempotency marker.
- **`visits.purged_at`** (nullable timestamptz) — scrub idempotency marker.
- **New role `vms_purge`** (`app/db/roles.sql` + grants in `0005`): `NOBYPASSRLS`, `SELECT` on `tenants`+`retention_policies`, `UPDATE` on `users`+`visits` (scrub), `DELETE` on `outbox_messages`+`portal_contact_verifications`, `INSERT` on `audit_events`. No BYPASSRLS, no privileges beyond the purge's needs.

### API/AsyncAPI delta
None. Both operations are ops commands (`scripts/`), not endpoints (Constraint 2). No new permission (the ops role is the authorization boundary, as for `scripts/bootstrap_tenant.py`).

## Part C — Plan

### Definition of done
- All 4 Gherkin scenarios pass, against **synthetic data only**.
- **Structural isolation:** the purge/erasure run as `vms_purge` (NOBYPASSRLS) with a per-tenant `SET LOCAL app.current_tenant_id`; a test proves that with tenant A's GUC set, a scrub/delete cannot affect tenant B's rows *even with the explicit predicate removed* (RLS+FORCE is the guarantee). Explicit predicates present as defense-in-depth.
- **Reference timestamps:** `users.disabled_at` added + set by the disable path; purge uses disabled_at/decided_at/created_at per the Risks mapping; a test proves fresh rows (younger than retention by any clock) are byte-identical after `--execute`, per store.
- **Coverage (verified inventory):** `visits` scrub covers all six PII columns (incl. `purpose`); non-terminal/abandoned visits scrubbed by `created_at` max-age (orphaned NULL-host covered); `outbox_messages` purged by age across all statuses; `users` scrubbed by `disabled_at`+window (email/display_name/external_idp_subject → per-row-unique redacted markers satisfying NOT-NULL/unique); `portal_contact_verifications` deleted by age. Each directly tested.
- **Idempotency:** `purged_at` excludes already-scrubbed rows; a second run and a crash-mid-run-then-rerun both touch 0 additional rows and write no duplicate counts — tested.
- **Erasure completeness + carve-out:** subject gone from every anchor (visits scrubbed; contact-verifications + outbox by visit_id AND verification_id deleted; staff subject scrubs the `users` row); cross-tenant subject untouched; on-site (`CheckedIn`/`Safe`) subject refused — all tested.
- **Audit hygiene:** each `retention.purge` (per tenant) and `retention.erasure` event fills the NOT-NULL columns as specified, carries counts/policy in `details`, and contains **no PII and no recoverable contact** (erasure `subject_ref` is a keyed HMAC) — directly asserted.
- **`--dry-run` default:** a dry run mutates zero rows / writes zero audit; `--execute` requires the typed tenant-slug confirmation + non-prod assertion — tested (refuses without them).
- `0005` migration has a tested `downgrade()`; new table has tenant col+index+unique+RLS enable/force; new columns nullable/additive; `vms_purge` role + grants applied; `/confirm-schema` passes; a run grep proves **only** `app/domain/retention/` + the ops scripts scrub/delete these tables.
- No secrets/PII in logs or in audit `details`.

## Three questions

**1. What was the hardest decision in this plan?**
The tenant-isolation safety model. The initial draft ran the purge under `BYPASSRLS` with "an explicit tenant predicate on every query" as the sole defense — which the security review correctly rejected for an irreversible cross-tenant DELETE, because a behavioral test can't prove the invariant and this is the exact missing-predicate class US-13a already hit (caught only by a FORCE-RLS backstop that BYPASSRLS removes). The revision introduces a dedicated `vms_purge` role that is *subject to* RLS and runs a per-tenant `SET LOCAL` GUC loop, so FORCE RLS structurally scopes every statement to one tenant even if a predicate is forgotten. It costs a new role + a session helper, but it turns "we tested that the queries we wrote are scoped" into "the database cannot let any query touch another tenant" — the right posture for an operation you can't undo.

**2. What alternatives were rejected, and why?**
- **Predicate-only isolation under BYPASSRLS** — rejected (see Q1): no structural backstop for an irreversible op.
- **Autonomous scheduled purge activating on merge** — rejected: sensitive irreversible ops never run autonomously (AGENTS.md); ops command + dry-run + human activation instead.
- **Hard-deleting expired `users`/`visits` rows** — rejected: `users` has inbound FKs and both anchor the append-only audit trail; scrub-in-place preserves purpose-limitation without orphaning the evidence DPDP depends on.
- **A bare `sha256(contact)` erasure `subject_ref`** — rejected: reversible for low-entropy contacts and lands in the forever-store; keyed HMAC (or counts-only) instead.
- **Scrubbing only the hand-listed visit columns** — rejected: it missed `purpose` (visitor free text); the scrub set is derived from a verified column inventory.
- **Purging outbox only for `pending`/`failed`** — rejected: an inverted predicate that leaves every `dispatched` row's encrypted PII+credential forever; purge by age across all statuses.
- **Splitting purge and erasure into two stories** — offered; the human chose one combined US-07; kept lean (~19 files, still under 25) as one story.

**3. What's the least confident part of this plan?**
The compliance-owner decisions the mechanism cannot ratify: the final retention windows, whether Indian DPDP treats anonymization-in-place as satisfying erasure per category, the exact life-safety carve-out for erasing an on-site visitor, and whether the scrubbed skeleton + retained `tracking_reference`/audit trail + keyed-HMAC subject_ref together constitute a re-identification path. The mechanism is built to make each of these a config/parameter/policy change rather than a rewrite, and every one is surfaced for sign-off — but the story genuinely cannot claim DPDP-complete until that human review happens, which is exactly why the DPDP sign-off stays a tracked GA gate this story does not close.

## Design-gate disposition
Two independent cold reads (domain-architect, security-privacy-reviewer; full reports in `docs/reviews/US-07-review.md`) produced **6 Blocking** findings on the initial draft. All are folded into this revision:
- **SP-B2** (BYPASSRLS isolation) → dedicated `vms_purge` NOBYPASSRLS role + per-tenant GUC + FORCE-RLS structural backstop (Core safety design; Q1).
- **DA-B1** (no reference timestamp) → add `users.disabled_at` (set on disable) + defined per-store clock; forward requirement for a `visits` checkout timestamp noted.
- **SP-B3** (incomplete coverage) → `purpose` added via verified column inventory; non-terminal/abandoned visits scrubbed by `created_at` (orphaned NULL-host covered); outbox purged by age across all statuses.
- **DA-B3** (erasure misses OTP-dispatch outbox) → cascade deletes outbox by visit_id AND verification_id.
- **DA-B2** (erasure vs on-site visit) → erasure refuses a `CheckedIn`/`Safe` subject; flagged for compliance-owner confirmation.
- **SP-B1** (reversible erasure subject_ref in forever-store) → keyed HMAC (reusing `hmac_hash.py`); no-recoverable-contact DoD assertion.

Should-fixes folded: `purged_at` idempotency marker (DA-S1), staff erasure path (DA-S2), no-PII-in-`details`-ever contract (DA-S3), per-tenant audit event filling NOT-NULL columns (DA-S4 + SP), `--execute` confirmation guard (SP), Compliance module ownership + cross-store-writer pre-declaration (DA-S5), `vms_purge` config read under the GUC (SP note). Compliance-owner sign-off items (final windows, on-site carve-out semantics, masking scheme, anonymization-vs-erasure re-identification) are surfaced in the plan/ADR-005 and remain part of the open DPDP GA gate — this story builds the mechanism and does not close that gate.
