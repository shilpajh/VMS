# US-10: SSO & Roles (Tenancy & Identity Schema)

**Status: Approved** (Human Gate 1 — approved 2026-07-23)

## Part A — Intent

### Problem
Today the Smart VMS repo has no real database schema at all — Day-0 bootstrap (`/bootstrap-environment`) deliberately created only an empty Alembic baseline migration and scaffolded FastAPI/React/Flutter shells, explicitly leaving the first real schema for this story because it has tenancy impact (per AGENTS.md's Quick Flow threshold: tenancy impact is never Quick Flow). There is no way to represent a tenant, authenticate a staff user, or check "does this user have permission to do X" — which blocks every other story, since AGENTS.md's non-negotiable rule ("Tenant scoping is mandatory on every query and endpoint") and the state machine's own `required_permission: approve_deny_holds` guard on Held-exit transitions both presuppose this schema exists.

**No PRD document is checked into this repo.** The only grounding for "US-10" is its name ("SSO & roles") and description across AGENTS.md/README/skill files: "the first REAL migration (tenants, users, roles)." This plan is built from that plus the project's architecture rules (Azure-first/Entra ID, the portal list in `frontend-react.md`, the state machine's permission requirement) — it is explicitly a design proposal for Gate 1, not a PRD-derived spec. See ADR-001's "Inferred vs. sourced" section for exactly which claims are grounded in a repo file versus proposed here.

### Solution
Introduce the Tenant & Identity domain: a `tenants` table (the isolation root), tenant-scoped `users` (staff only, SSO-authenticated via Entra ID — no passwords), a tenant-global RBAC catalog (`roles`, `permissions`, `role_permissions`), a tenant-scoped `user_roles` assignment table, and the first cut of the append-only `audit_events` table. Staff authenticate via Entra ID OIDC (Authorization Code + PKCE, MSAL in the React SPA); a validated bearer token resolves to exactly one tenant and one user; authorization checks resolve permissions through the role assignment chain. A `GET /me` endpoint and tenant-scoped user/role-management endpoints let a `tenant_admin` manage their own tenant's users and role assignments.

Full design rationale, rejected alternatives, and the RLS/RBAC/audit mechanics are in **ADR-001** (`docs/architecture/adr/ADR-001-tenancy-identity-schema.md`) — required per AGENTS.md's ADR trigger list (tenancy schema, security posture). This plan document does not repeat that reasoning; Part B summarizes only the contract deltas an implementer/verifier needs.

### Out of scope (explicit scope-creep fence)
- **Tenant creation and first-admin provisioning are NOT an API/UI feature in this story.** They happen via an internal ops/seed script run under a `BYPASSRLS` role — no cross-tenant "platform operator" role or endpoint exists anywhere in this story's file map. (Decided; see ADR-001 §4.)
- **Per-tenant custom roles, group-claim→role auto-mapping, SCIM provisioning** — fixed system roles only, admin-assigned. Deferred.
- **Entra B2B/guest staff** — native tenant members only in this cut; guest mapping deferred.
- **Site-scoped roles** — no `sites` table yet; roles are tenant-wide.
- **Visitor-facing anything.** The public request portal is unauthenticated and out of scope; visitors are never rows in this schema.
- **MFA/conditional access, local/password auth** — delegated to Entra policy / never built, respectively.
- **Full audit-table partitioning/retention machinery** — this story introduces only the append-only core `audit_events` needs; partitioning/reporting is a later Audit & Reporting story (flagged as ADR-001 open question O2, non-blocking).
- **Service/machine identities, API keys** — the C# edge connector's outbound-only mTLS is a separate, already-decided mechanism (AGENTS.md).

### Risks (non-obvious failure modes)
- **RLS is easy to get subtly wrong.** A `USING`-only policy (no `WITH CHECK`) would still allow cross-tenant writes; the two-argument `current_setting(..., true)` form fails open (returns NULL → empty result, not an error) instead of failing closed. ADR-001 §1 pins both details explicitly — implementers must not "simplify" this during execution.
- **Composite FK prerequisite is non-obvious.** `user_roles`'s composite FK `(user_id, tenant_id) → users(id, tenant_id)` will fail to create unless `users` has an explicit `UNIQUE (id, tenant_id)` constraint (redundant with the PK) — easy to omit and get a confusing Postgres error instead of a design failure.
- **Stateless tokens don't self-revoke.** A disabled user's still-valid Entra access token remains technically "valid" until it expires unless the app re-checks disabled/suspended status against current DB state on every request. This is a real gap if implemented naively (issue-token-once, trust-until-expiry).
- **JIT-zero-roles is correct but has a UX cliff**: a newly-SSO'd user who hasn't been assigned a role yet will authenticate successfully and then get 403 on everything. The frontend must render this state clearly ("no roles assigned yet, contact your admin") rather than looking like a bug.
- **The retention window (180 days) and India-region default are explicitly a placeholder**, not compliance-signed-off policy — a careless implementation would treat this as final rather than flagging it for real DPDP sign-off before GA (ADR-001, Consequences).

### Statemachine impact
None. `packages/contracts/statemachine/visit-lifecycle.yaml` is unchanged. This story makes `required_permission: approve_deny_holds` (already present on both Held-exit transitions) resolvable for the first time, by making `reception_security` the role that grants it — a compatibility guarantee, not a state-machine edit.

### API contract delta (packages/contracts/openapi/identity.yaml — new file)
High-level surface (full OpenAPI schema is an execute-story task, not written here):
- `GET /me` → `{ id, tenant_id, display_name, roles[], permissions[] }`. 200 authenticated; 401 no/invalid/expired token, or token whose `tid` doesn't match its resolved tenant's `entra_tenant_id`, or tenant suspended.
- `GET /roles`, `GET /permissions` — read tenant-global catalogs. 200 authenticated.
- `GET /tenants/{tenant_id}/users` — list. Requires `manage_users`. **403** if the authenticated principal's tenant ≠ `{tenant_id}` (mandatory per `contracts.md`).
- `POST /tenants/{tenant_id}/users` — invite/provision. Requires `manage_users`. 403 tenant mismatch.
- `PATCH /tenants/{tenant_id}/users/{user_id}` — enable/disable. Requires `manage_users`. 403 tenant mismatch; 404 unknown user (never leak existence across tenants — a cross-tenant lookup returns 403, not 404, so as not to distinguish "wrong tenant" from "no such user under the resolved tenant").
- `GET /tenants/{tenant_id}/users/{user_id}/roles`; `POST .../roles` assign; `DELETE .../roles/{role_id}` revoke. Requires `manage_roles`. 403 tenant mismatch.
- **No `POST /platform/tenants` or any cross-tenant endpoint exists** — tenant creation is ops-script only (ADR-001 §4).

### Event/audit contract
Every one of `tenant.created`, `user.provisioned`, `user.enabled`, `user.disabled`, `role.assigned`, `role.revoked` is an append-only row in `audit_events` with `{ actor, timestamp, correlation_id, reason, target_type, target_id, policy_version (role changes only) }` — the same 5-field shape `backend-python.md` mandates for every high-risk action, matching what the visit state machine already does.

### Gherkin scenarios

```gherkin
Feature: Staff SSO login and role-based access (US-10)

  Background:
    Given tenant "acme" exists with entra_tenant_id "acme-entra-tid"
    And tenant "globex" exists with entra_tenant_id "globex-entra-tid"
    And user "priya@acme" belongs to tenant "acme" with role "reception_security"

  Scenario: First-time SSO login JIT-provisions a user with zero roles
    Given no user exists yet for Entra subject "new-oid" in tenant "acme"
    When a valid Entra token for tenant "acme" with oid "new-oid" calls GET /me
    Then the response status is 200
    And a new user row is provisioned in tenant "acme" with zero roles and zero permissions
    And an audit event "user.provisioned" exists with actor "new-oid" and correlation_id

  Scenario: Cross-tenant isolation on user management
    Given user "priya@acme" is authenticated with a valid token for tenant "acme"
    When "priya@acme" calls GET /tenants/globex/users
    Then the response status is 403
    And no row from tenant "globex" is ever returned

  Scenario: Permission resolution matches the state machine's requirement
    Given user "priya@acme" has role "reception_security"
    When the domain layer checks has_permission("priya@acme", "acme", "approve_deny_holds")
    Then the result is true
    And a user with only role "host" checking the same permission gets false

  Scenario: Disabled user is rejected on next request despite a still-valid token
    Given user "priya@acme" is disabled by a tenant_admin
    And "priya@acme" holds an Entra access token that has not yet expired
    When "priya@acme" calls GET /me with that token
    Then the response status is 401
    And an audit event "user.disabled" exists with actor, reason, and correlation_id
```

## Part C — Plan

### Definition of done
- All Gherkin scenarios above pass as executable tests (state-machine-style: valid/invalid permission resolution, tenant isolation, JIT provisioning, stateless-revocation re-check).
- `/confirm-schema US-10 <migration-file>` passes every checklist item — tenancy (tenant_id + index on every tenant table, or explicit tenant-global justification), audit append-only grants, migration rollback tested, module-boundary (Tenant & Identity + shared `audit_events` sink pre-declared, per ADR-001 §2).
- `alembic upgrade head` then `alembic downgrade -1` both run cleanly in the local dev environment (docker-compose from Day-0 bootstrap).
- RLS is provably fail-closed: a query issued with `app.current_tenant_id` unset raises rather than returning all rows.
- `pytest` suite covers: tenant isolation (403), permission resolution (true/false cases matching the seed table), JIT provisioning with zero roles, stateless-revocation re-check (disabled user + valid token → 401), audit-event presence with all 5 required fields on every identity action.
- No secrets (Entra client ID/secret, signing config) appear in code, fixtures, or logs — confirmed by security-privacy-reviewer at `/verify-story`.

### User journey (demo path)
1. Ops runs `scripts/bootstrap_tenant.py --tenant acme --admin-email admin@acme.example` against the local dev DB → tenant `acme` + one `tenant_admin` user exist.
2. A staff user opens the web app, MSAL redirects to Entra, signs in, returns with a token.
3. `GET /me` succeeds (200), the SPA shows the user's roles (initially just `tenant_admin` for the seeded admin).
4. The admin calls the (not-yet-built-UI, but API-testable) role-assignment endpoint to grant a second user `reception_security`.
5. That second user logs in for the first time → JIT-provisioned with zero roles until the assignment lands, then sees `reception_security`'s permissions once assigned.
6. A user from `globex` attempting to query `acme`'s users gets 403.
7. An admin disables a user; that user's still-valid token is rejected (401) on the next call.

1. **Provision DB roles** (`app/db/roles.sql` + local docker-compose init): non-superuser RLS-subject app role, separate `BYPASSRLS` role. Test: connecting as the app role and attempting a cross-tenant `SET LOCAL` bypass fails.

5. **Entra token validation** (`app/auth/entra.py`) — vendor/SSO integration task. Test: valid token accepted; wrong `aud` rejected; `tid` mismatch rejected; expired token rejected; unknown/suspended tenant rejected (all 401).

9. **Audit events** on every identity action (`user.provisioned`, `user.enabled`, `user.disabled`, `role.assigned`, `role.revoked`, `tenant.created`). Test: all 5 required fields present; append-only (no UPDATE/DELETE grant) verified.
10. **Stateless-revocation re-check** — disabled/suspended status checked against current DB state on every request, not cached from token-mint time. Test: the Gherkin scenario above (disabled user + valid token → 401).
11. **Ops bootstrap script** (`scripts/bootstrap_tenant.py`), run under `BYPASSRLS`. Test: creates tenant + admin + seeds `platform` sentinel tenant + `role_permissions` catalog; confirms it is not reachable via any HTTP route.
12. **Frontend MSAL wiring** (`src/auth/msal.ts`, `useCurrentUser.ts`) with in-memory token storage. Test: `vitest` — token never touches `localStorage`/`sessionStorage` (grep/spy assertion); "no roles yet" state renders distinctly from an error state.

## Three questions

**1. What was the hardest decision in this plan?**
Where to put the tenant-bootstrap problem. JIT-zero-roles is the right least-privilege default, but it creates a genuine chicken-and-egg gap (nobody can grant the first tenant_admin their role) that has no answer inside a normal "everything is tenant-scoped" API without either (a) breaking the tenant-isolation invariant with a cross-tenant role, or (b) punting to an out-of-band mechanism. We chose (b) — an ops script under `BYPASSRLS`, with zero code-level cross-tenant surface — specifically to avoid introducing the one exception that would make every other "cross-tenant access is a blocking defect" rule in the codebase have an asterisk on it.

**2. What alternatives were rejected, and why?**
- **Schema-per-tenant/database-per-tenant** instead of shared-schema + RLS: rejected for migration-multiplication cost, cross-schema reporting joins, and because it contradicts the modular-monolith/YAGNI default in AGENTS.md's Engineering philosophy for a first cut with no proven need for physical isolation yet.
- **A "platform operator" cross-tenant role/endpoint** for tenant bootstrap: rejected in favor of the ops-script approach, specifically to avoid building the one deliberate tenant-isolation exception into the running application before there's a proven need for self-service tenant onboarding (this is enterprise B2B VMS — tenants are onboarded by ops/sales, not self-serve signup).
- **Server-side BFF/session-cookie auth** instead of SPA-direct token acquisition: rejected for this first cut on complexity grounds (a whole new backend session-management component) in favor of SPA-direct with in-memory-only token storage as a lighter-weight mitigation for the XSS-token-theft concern the BFF would otherwise solve more completely. This trade-off is revisitable if the admin-facing surfaces later prove to need stronger protection.

**3. What's the least confident part of this plan?**
The exact role → permission seed (`tenant_admin`, `host`, `reception_security`, `dashboard_viewer` and their permission bundles) is inferred, not PRD-sourced — there is no PRD in this repo to check it against. It covers the one permission the state machine already requires (`approve_deny_holds`) and the portal list in `frontend-react.md`, but it has no warden/muster role for the `muster_marked_safe` transition and no distinct second-approver permission for the dual-sign-off path — both of which exist in the state machine already. The `permission_policy_version` mechanism is designed to make extending this seed non-breaking, but the initial taxonomy itself is a judgment call that should be checked against real product requirements as soon as a PRD exists, not treated as final.
