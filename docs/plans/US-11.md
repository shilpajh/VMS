# US-11: Website Pre-registration Visibility

**Status: Approved** (Human Gate 1 — approved 2026-07-23)

## Part A — Intent

### Problem
Today the visit lifecycle exists only as a contract (`packages/contracts/statemachine/visit-lifecycle.yaml`) and has no implementation — there is no `visits` table, no way for a visitor to submit a pre-registration, and no way for a host to approve or deny one. This is the first story to implement any part of the canonical state machine: the `Requested → Registered` and `Requested → Denied` transitions, plus the public, unauthenticated portal submission endpoint that creates a visit in `Requested` in the first place.

`specs/features/US-11-portal-visibility.feature` already exists (pre-written, checked in) and is the acceptance-criteria source of truth for this story — this plan does not re-derive it, it implements against it.

### Solution
A tenant-scoped `visits` table (following ADR-001's established RLS/tenancy pattern) plus: an unauthenticated public portal endpoint that creates a `Requested` visit with concrete rate-limiting and Cloudflare Turnstile bot protection (both mandatory per AGENTS.md's public-portal guardrail, not optional hardening); authenticated host `approve`/`deny` endpoints (reusing US-10's `get_current_principal`/RBAC infra) that transition the visit and, on approval, issue a check-in code dispatched asynchronously via a new transactional-outbox table (`ADR-002`); a `GET /visits` list gated by a new `view_visits` permission for reception/security and tenant admins, with hosts seeing only visits they're assigned to; and full audit coverage for `visit.requested`/`visit.registered`/`visit.denied`.

Two ADRs govern this story: **ADR-001** (already approved, reused verbatim for the `visits` and `outbox_messages` tables' tenancy pattern) and **ADR-002** (new — the transactional outbox and `visit.checkin_code.dispatch` notification contract, written for this story). Both went through the same design-gate rigor as US-10: domain-architect drafted, security-privacy-reviewer cold-read the design (`docs/reviews/US-11-review.md`), four judgment calls were escalated to and decided by the human product owner, and the design was revised to close every finding before this plan was assembled.

### Sequencing dependency (critical — read before starting execution)
**`feature/US-11` must branch from `feature/US-10`, not `main`** — `main` doesn't have the `tenants`/`users`/RBAC schema this story depends on, and `feature/US-10` isn't merged yet. This is a normal stacked-branch situation, not a workaround.

**Hard merge/ship gate, not just a sequencing note:** `feature/US-10` has one open Blocking security finding (`docs/reviews/US-10-review.md`, B1 — an Entra token-validation defect allowing forged cross-tenant authentication). US-11's host endpoints (`approve`/`deny`/`GET /visits`) derive their tenant/ownership checks entirely from the same `get_current_principal` function US-10's B1 lives in. **US-11 may be built and unit-tested on this branch now, but neither US-10 nor US-11 may merge to a release branch or deploy until US-10's B1 is remediated.** This plan's Definition of Done includes a US-11-specific forged-token test (not just inheriting US-10's) precisely because "the diff looks fine" doesn't prove the shared dependency is safe.

### Out of scope (explicit scope-creep fence)
- **No actual portal/host UI screens.** Every acceptance criterion in the Gherkin file is API/DB/audit-level (status codes, record state, audit events) — none names a UI. Building the actual React public-submission form and host-approval screen is a separate, follow-up UI story; this story is backend-only (API + domain + migration + contracts), matching how US-10 scoped its own frontend piece to the minimum needed to prove the wiring.
- **No tracking-reference lookup endpoint.** Re-checked against the Gherkin file: all 5 scenarios require only *issuance* of a tracking reference, never a visitor looking up status by it. Building one now would be speculative (YAGNI) and would need its own rate-limiting/entropy analysis later if a story actually needs it.
- **No reception-triage UI/endpoint for NULL-host (unresolved-host) visits.** The schema supports it (`host_user_id` nullable) but no endpoint surfaces these to reception in this cut — flagged as a real but deferred gap, not silently dropped.
- **No relay worker implementation.** This story writes the outbox row (the domain intent) inside the approval transaction; the actual `services/workers/` relay that reads pending rows and calls a real notification vendor is separate follow-on work with its own security review (ADR-002 explicitly scopes this out and flags the worker's tenant-context strategy as an open question for when it's built).
- **No notification vendor chosen or integrated.** Only the async boundary and message contract (ADR-002) are decided. Not a biometric/OCR/CCTV/access-control vendor, so no POC-skill gate applies — but no vendor SDK is added in this story regardless.
- **No `CheckedIn`/`Held`/dual-signoff/muster transitions.** This story only implements `Requested → {Registered, Denied}`. The rest of the state machine is later stories' work.
- **No self-service tenant `public_slug` management UI.** The `tenants.public_slug` column (new, needed for the public portal URL) is added via migration/seed, not a tenant-admin-editable feature in this cut.

### Risks (non-obvious failure modes)
- **The shared-dependency risk above (`get_current_principal`) is the single biggest risk in this plan** — it's not something US-11's own code can fix; it's a merge-order discipline that has to be honored by whoever runs `/document-story`/Gate 2 for either branch.
- **Anti-enumeration is easy to get subtly wrong.** The design deliberately returns a uniform response regardless of whether `host_hint` resolves to a real host, and uniform `403` (never `404`) on cross-tenant visit lookups — a careless implementation could leak host-existence or visit-existence through a timing difference or an inconsistent error path. Verifiers must check this explicitly (AC-2), not just the happy path.
- **PII must not leak into the append-only audit table.** `visit.denied`'s audit `reason` is a coded value + a `visits.id` reference, NOT the host's free-text denial reason verbatim — because `audit_events` is purge-exempt and the free-text can contain visitor PII. Getting this backwards (storing free text in the audit row) silently defeats erasure and is easy to miss in a naive implementation.
- **The check-in code is a credential, not a convenience string.** It's a `secrets.token_urlsafe(24)` opaque token, hashed (SHA-256) on the `visits` row, and only ever handled in plaintext transiently (generated → put in the encrypted outbox payload → discarded). A careless implementation could accidentally log it, store it in plaintext somewhere, or return it in an API response.
- **File count is large for one story** (migration + models + domain + auth/security + API + contracts + ~10 new test files, backend-only). `/execute-story`'s guardrail is `max_files_changed: 25`; this plan is close to that ceiling. Flagged explicitly rather than silently risking a mid-loop guardrail trip — execute-story may reasonably need more than one internal iteration to land it all with tests-first discipline, which is within its own 3-iteration budget.

## Part B — Contracts

### ADRs
- **ADR-001** (already approved) — reused verbatim for `visits`/`outbox_messages` tenancy pattern (RLS `ENABLE`+`FORCE`, `USING`+`WITH CHECK`, fail-closed single-arg `current_setting`, composite-FK cross-tenant prevention pattern).
- **ADR-002** (new, this story) — `docs/architecture/adr/ADR-002-transactional-outbox-notification-contract.md`. The `outbox_messages` table contract, the deterministic idempotency-key scheme (`sha256("visit.checkin_code.dispatch:" + visit_id)`), the AsyncAPI `visit.checkin_code.dispatch` message shape, the staleness/expiry send-gate, Key-Vault envelope encryption for the payload (credential + PII at rest), and the Visitor&Visits-writes/Integration-relays module split.

**Design-gate review summary** (full findings in `docs/reviews/US-11-review.md`):

### Statemachine impact
`packages/contracts/statemachine/visit-lifecycle.yaml` is **unchanged** — this story implements two already-defined transitions (`host_approval`, `host_denial`), it doesn't add or modify any. No new ADR needed for the state machine itself.

### API contract delta (`packages/contracts/openapi/visits.yaml` — new file)
- `POST /public/portal/{tenant_slug}/visit-requests` — **unauthenticated**. Body: visitor name, contact channel+value, host hint, privacy-notice acknowledgment (required `true`) + version, Turnstile token, optional `Idempotency-Key` header. Turnstile verified **before** tenant-slug resolution (avoids a slug-validity timing oracle) and before any DB work. Returns `202` + `tracking_reference` only — no host data, no confirmation of host existence, uniform response whether the host resolves or not. `429` on rate-limit exceeded (per-IP ~5/min burst 10, per-tenant-slug ~60/min — gateway primary, in-app Redis token-bucket defense-in-depth). `400` on missing/invalid Turnstile token, no DB write. Unknown/suspended `tenant_slug` → uniform `404`.
- `POST /visits/{visit_id}/approve` — authenticated, requires `approve_deny_visits`, host-owns-this-visit check (`visit.host_user_id == principal.user_id`). `409` if the visit isn't currently `Requested` (guarded conditional UPDATE, race-safe). Triggers the code issuance + outbox write + `visit.registered` audit, all one transaction.
- `POST /visits/{visit_id}/deny` — same auth/ownership; `reason` required in body (`422` if missing/empty). `409` if not `Requested`. No credential created.
- `GET /visits` — authenticated. A caller with `view_visits` (reception_security/tenant_admin) sees the full tenant-scoped list; a caller with only `approve_deny_visits` (host) sees only visits where they're the assigned host.
- `GET /visits/{visit_id}` — uniform `403` whether the row belongs to another tenant or doesn't exist at all (never `404`, so cross-tenant existence is never an oracle). Visible row → `200`.

### Event contract (`packages/contracts/asyncapi/visit-checkin-dispatch.yaml` — new file)
`visit.checkin_code.dispatch` per ADR-002 §3 — `schema_version`, `tenant_id`, `visit_id`, `correlation_id`, `idempotency_key`, `contact_channel`, `contact_value`, `checkin_code` (plaintext, transient), `tracking_reference`, `code_expires_at`, `tenant_display_name`. No `site`/`device` (those belong to the later edge-connector command family).

### RBAC delta (small, additive — amends US-10's seed, does not redesign it)
New `permissions` row: `view_visits` (`"View all visits within a tenant"`). New `role_permissions` rows: `reception_security → view_visits`, `tenant_admin → view_visits`. `PERMISSION_POLICY_VERSION` bumped (`"v1"` → `"v2"`), recorded on any future role-change audit event. This is a Tenant & Identity table touched by a Visitor & Visits story — flagged explicitly (not silently done) per module-boundary discipline; it's a pure additive seed change, not a redesign of US-10's RBAC model.

### Gherkin scenarios
The full scenario set is `specs/features/US-11-portal-visibility.feature` (pre-existing, unmodified). Reconciliations for implementers/QA, not new scenarios:
- **Scenario 3/4's `actor "rahul@acme"`**: the audit `actor` column stores the host's **stable id** (`user_id`/`external_idp_subject`), never the email (PII, forbidden in the purge-exempt audit table per the US-10 precedent). QA asserts against the resolved stable id of the seeded `rahul@acme` fixture user, not the literal string.
- **Scenario 1's "live visitor list"**: verified by querying as a `view_visits`-holding principal (e.g. a seeded `reception_security` user) or as the owning host — either satisfies the scenario; querying as an unrelated host without `view_visits` and without ownership does not.
- **Scenario 5's 409**: the concrete verifier call is `POST /visits/{id}/approve` (or `/deny`) on a visit already past `Requested` — there is no route that accepts an arbitrary target status or the `checkin_verified` trigger at all (that's the actual safety property; such a call would be `404`/`405`, not `409`).

## Part C — Plan

### Definition of done
- All 5 scenarios in `specs/features/US-11-portal-visibility.feature` pass as executable tests, with the reconciliations above applied.
- **US-11-specific forged-token/wrong-`tid` cross-tenant test** passes against `/visits/{id}/approve`, `/visits/{id}/deny`, and `GET /visits` directly (not inherited from US-10's identity-route tests) — proves the new surface rejects a forged principal, whether or not US-10's B1 fix has landed yet.
- Rate-limiting (`429`) and Turnstile-verification (`400` on failure, no DB write, verified before tenant-slug resolution) both have passing tests.
- Anti-enumeration: uniform response on unresolved host_hint; uniform `403` (never `404`) on cross-tenant visit lookup; both directly tested.
- `visit.denied` audit row contains a coded reason + `visits.id` reference, never the host's free-text verbatim — directly tested.
- Check-in code: only its SHA-256 hash is ever persisted on `visits`; the outbox payload is envelope-encrypted `BYTEA`, never cleartext; a test confirms no plaintext code or contact value appears in any log output.
- Outbox idempotency: redelivering the same `idempotency_key` results in exactly one dispatched notification (simulated, since the relay worker itself isn't built in this story — test the write-side dedup and the documented contract).
- `0002_visits` migration (visits + outbox_messages + `view_visits` RBAC seed) has a tested `downgrade()`; both tables are RLS-enabled+forced with `USING`+`WITH CHECK`; `/confirm-schema` passes for both tables.
- No secrets (Turnstile secret key, envelope-encryption key ref) in code/fixtures/logs.

### User journey (demo path)
1. Ops/seed script sets `tenants.public_slug` for a demo tenant (amend `scripts/bootstrap_tenant.py` or a follow-up seed step).
2. An anonymous visitor `POST`s to `/public/portal/acme-corp/visit-requests` with a valid Turnstile token, naming host `rahul@acme` → `202` + a `REQ-` tracking reference; a `Requested` visit exists.
3. A `reception_security` user (with `view_visits`) calls `GET /visits` and sees it in the tenant's live list within 2 seconds.
4. Host `rahul@acme` calls `POST /visits/{id}/approve` → visit becomes `Registered`, a check-in code is generated (hash persisted, plaintext only in the encrypted outbox row), `visit.registered` audit written.
5. A `globex` user attempting `GET /visits/{id}` on that visit gets `403`.
6. A second submission naming a denial gets `POST /visits/{id}/deny` with reason `"unknown visitor"` → `Denied`, `visit.denied` audit with a coded reason (not the free text) + reference to the visit row, no credential created.
7. A direct `POST /visits/{id}/approve` retried on an already-`Registered` visit → `409`, status unchanged.

## Three questions

**1. What was the hardest decision in this plan?**
Whether US-11 could proceed at all while US-10's auth-bypass finding is still open. The resolution — build and unit-test on the stacked branch now, but treat the fix as a hard merge/ship gate for *both* stories, and prove US-11's own endpoints reject a forged token rather than assuming inheritance from US-10's tests — came directly from the security review catching that "the diff looks fine" doesn't prove a shared dependency is safe. That's the one finding in this plan that isn't a code-level fix; it's a process constraint on when this work is allowed to ship.

**2. What alternatives were rejected, and why?**
- **Waiting for US-10's B1 fix before starting US-11 design/implementation at all**: rejected — the fix and this story's design/build are independent work streams (the public path doesn't touch auth at all; the host path can be built and unit-tested locally against the existing, if-flawed, `get_current_principal` contract). Blocking all forward progress on one open finding would be more conservative than the actual risk warrants, as long as the merge gate is real and enforced, not just documented.
- **Host-only visibility for `GET /visits`** (no `view_visits` permission, no RBAC migration): rejected in favor of adding the permission, because a real front desk needs to see everyone expected at the site, not just visits a specific host happens to own — the narrower default would have made Scenario 1 pass only under an artificially narrow verifier query, not reflect how reception actually works.
- **Storing the host's free-text denial reason directly in the audit event** (simplest implementation, matches the Gherkin's literal wording most directly): rejected because `audit_events` is purge-exempt and append-only — a free-text reason can carry visitor PII that would then never be erasable, defeating the retention/purge story before it's even built.
- **A short numeric check-in code with keyed-HMAC hashing**: rejected in favor of a long opaque token with a plain SHA-256 hash, because a long-token design avoids needing attempt-limiting/HMAC machinery in this story at all, deferring that complexity to whichever later story builds actual code verification.

**3. What's the least confident part of this plan?**
The file count and scope boundary between "this story" and "the relay worker." The design deliberately stops at writing the outbox row and defines the contract the worker must honor (ADR-002), but doesn't build the worker — that's a clean boundary on paper, but it means this story ships an outbox table that nothing drains yet, and the "idempotency" acceptance criterion for dispatch is necessarily a write-side/contract test rather than an end-to-end proof that a redelivered message really sends once. That gap is intentional (relay worker is explicitly out of scope) but is worth the human approver's attention — if the real intent was to see a working end-to-end notification in this story, the scope needs to grow, not just the file map.
