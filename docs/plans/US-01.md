# US-01: Pre-registered Check-In (QR, hardware-free slice)

Status: Approved (Human Gate 1, 2026-07-24 — approved via direct `/execute-story US-01` invocation)

## Part A — Intent

### Problem
A `Registered` visit (host-approved, check-in code issued via US-11) has no way to become `CheckedIn`. `packages/contracts/statemachine/visit-lifecycle.yaml` already reserves the `Registered -> CheckedIn` edge (`checkin_verified` trigger, guards `[identity_verified, watchlist_clear, within_visit_window]`) but nothing implements it — `app/domain/visits/state_machine.py`'s transition table only wires the two US-11 portal edges. There is also no credential-intent recording, no host-arrival notification, and no authenticated staff-facing UI at all yet (US-11 shipped API-only; US-11's memory entry explicitly flags "host-approval UI story" as a separate, not-yet-built unblock).

PRD US-01's literal acceptance criteria assume a physical kiosk with face verification (`< 1.5s` face match, `< 30s` kiosk dwell). This wave is explicitly scoped hardware-free (per the user's Wave 1 direction: "US-01 (QR check-in, no face)") — no biometric vendor SDK, no Flutter kiosk build, no `/biometric-provider-poc`. This plan implements the QR-code path of US-01 only; the face-verification path is a distinct future story gated by CLAUDE.md's biometric-vendor POC/ADR requirement.

### Solution
Wire the `Registered -> CheckedIn` transition for the QR-code path:
- A reception/security-authenticated endpoint, `POST /visits/checkin`, that accepts a check-in code (decoded from a QR by any camera/scanner client-side — decoding itself is out of this story's scope), validates it against the `Registered` visit it belongs to, applies the three contract guards, transitions the visit, and — in the same transaction — records a **credential-grant command** (cloud-side intent only, per AGENTS.md's "cloud records intent, edge executes" rule) and a **host-arrival-notification** outbox message, then writes the `visit.checked_in` audit event.
- A minimal authenticated React page (`apps/web`) where reception/security staff enter/paste the code and see the result — the demo surface for this story, not a kiosk and not the broader host-approval dashboard.

### Out of scope (explicit scope-creep fence)
- **Face/fingerprint/iris verification** (US-01's literal AC, US-12) — no biometric vendor SDK, no consent-capture UI, no `/biometric-provider-poc` run. `identity_verified` is satisfied by check-in-code possession (a bearer secret only the invited visitor received) for this story only.
- **Real watchlist screening** (PRD 3.5) — `watchlist_clear` is a stub guard that always returns `True`, clearly named and commented, until the dedicated watchlist-screening story exists. **This is a Blocking item for any release that claims automated watchlist coverage** — flagged here so it cannot be mistaken for a shipped feature; `/verify-story` and `/release-readiness` must both re-surface it.
- **Zone/site administration** (PRD 3.10) — no `sites`/`zones` tables exist yet (`outbox_messages.site_id`/`device_id` are already reserved-nullable for this). The credential-grant command carries a fixed placeholder `zone: "site-default"` and `site_id/device_id: null` until the admin zone-configuration story ships.
- **Edge-connector consumption, physical badge printing, door release** — `apps/edge-connector` is still just a README scaffold. This story only writes the cloud-side command intent row, exactly the treatment US-11 gave `visit.checkin_code.dispatch` before any relay worker existed.
- **Actual host-notification delivery** (WhatsApp/SMS/email send) — recording the outbox intent only; delivery is the (not-yet-built) relay/notification worker's job, same scope cut US-11 already made. Host contact channel is `users.email` only — `users` has no phone/WhatsApp column yet.
- **Walk-in (US-02) and paper-slip (US-03) check-in** — different entry paths (`AwaitingApproval`), separate stories.
- **Full reception/host dashboard** — only the single check-in-action page; the broader dashboard is US-11's already-flagged future "host-approval UI story."
- **Flutter kiosk app** — no changes in this wave.

### Risks (non-obvious failure modes)
- **Stub guard visibility**: a `watchlist_clear` guard that always passes is exactly the kind of thing that must never be discovered by an attacker (or an auditor) before a teammate reads about it first. It must be a named function with a fixed, greppable marker (not a bare `True` inline), called out again in this story's `/document-story` memory entry, and re-checked at `/release-readiness`. Two things must be true about the stub, not just "it exists": (1) no field or audit event this story writes may assert or imply that a watchlist check was *performed and cleared* — a false "cleared" is worse than a visibly absent check; (2) the contract's separate `Registered -> Held` (`watchlist_match`) edge is **also** not wired this story, so the "uncertain outcome goes to Held for human review" control has no code path yet either — this is a second, distinct gap from the guard stub and both must be named in the release-blocker note, not just "watchlist returns True."
- **Check-in code is a bearer credential.** Unlike the public portal (unauthenticated, needed CAPTCHA + rate limiting), this endpoint is staff-authenticated (`checkin_visits` permission) — that materially reduces exposure, but the endpoint must still return one uniform "invalid or expired code" error for every failure reason (unknown hash, wrong tenant, expired, already consumed), never a distinguishable one, so it can never become a guessing oracle even for an authenticated-but-malicious staff account. The expiry check must be folded into the same guarded `UPDATE`'s `WHERE` clause as the hash/tenant/status predicates (`AND checkin_code_expires_at > :now`), not applied as a separate check-then-rollback step after the row is already flipped to `CheckedIn` — otherwise an expired-but-real code observably does more work (one row updated, then rolled back) than an unknown or wrong-tenant code (zero rows matched), which is exactly the kind of timing/behavior oracle US-11's review flagged for the portal endpoints. Folding expiry into the `WHERE` clause also makes a `NULL` `checkin_code_expires_at` fail closed for free (`NULL > :now` is never true in SQL) — the correct default for any pre-migration row that somehow lacks the column.
- **Single-use enforcement.** No new "consumed" flag is needed: the guarded `UPDATE ... WHERE status = 'Registered' AND checkin_code_hash = :hash AND checkin_code_expires_at > :now` (the same race-safe idiom `approve_visit`/`deny_visit` already use, extended with the expiry predicate above) makes a second attempt against an already-`CheckedIn` visit fail by construction — affected-row-count zero, not a second transition.
- **`within_visit_window` has no natural field yet, and the mapping is a known-interim substitution, not a correct one.** No story has built a scheduled visit-arrival window. This plan maps the guard onto a new persisted `visits.checkin_code_expires_at` column (mirroring the value already computed transiently in `approve_visit` and copied onto `outbox_messages.not_valid_after`) so the domain layer can enforce the guard by reading the `visits` row alone — never by reaching into `outbox_messages`, which is a dispatch artifact, not the domain's source of truth. But `checkin_code_expires_at` denotes *the deadline to arrive and use the code*, not *the visitor's expected arrival window* — the two are conflated here only because no scheduling story exists yet. This must be stated as an explicit, named interim substitution (in ADR-003), not a real implementation of the guard's contract meaning, so the next maintainer reading a guard named `within_visit_window` backed by a column named `checkin_code_expires_at` doesn't mistake the mismatch for a bug report.
- **The credential-grant command's `expiry` field has the same conflation, with a sharper consequence.** Reusing `checkin_code_expires_at` as the *granted credential's* validity window means a visitor who checks in on day 6 of a 7-day code gets a ~1-day badge, and one who checks in on day 1 gets a ~6-day badge — an arrival-time-dependent, not visit-duration-dependent, credential lifetime. Because AGENTS.md requires panel-side expiry to hold without cloud connectivity, a future edge connector will faithfully enforce this arbitrary expiry. This is a known-wrong placeholder (no visit-duration/end field exists yet to derive it from correctly) and must be flagged as an open question in ADR-003, not silently wired as if it were correct.
- **First authenticated UI screen beyond sign-in.** `apps/web` currently has no authenticated page at all past the MSAL sign-in/`/me` shell. Care is needed not to let "add one check-in page" grow into the broader host dashboard US-11 already deferred.
- **`credential_grant_command` is declared as a side effect of only one of `CheckedIn`'s four entry transitions.** `checkin_verified`, `approver_confirm` (walk-in), `both_approvals_received` (dual sign-off), and `security_release` (Held release) all reach `CheckedIn`, but this plan only wires the grant side effect on the first. That is correct scope for this story, but — unlike `credential_lifecycle`'s invariant, which forces `credential_deprovision_command` on *every* exit from `CheckedIn` — there is no contract invariant catching a future walk-in/dual-sign-off/hold-release story that checks a visitor in without ever granting a credential. ADR-003 must note this gap explicitly so it's caught by the contract later, not by luck.
- **The audit contract's `verification_method` field has no backing column** (`audit_events.reason` is the only free-text slot, and it already means "coded denial reason" elsewhere) — encoding it as `reason="qr"` satisfies the letter of the contract for this story (disambiguated by `event_type="visit.checked_in"`) but is audit-schema debt: once face/fingerprint verification exist, `reason` means two different things depending on `event_type`, and a real audit review querying "all QR vs. face check-ins" has to know to filter that way. Flag as debt for a future dedicated `verification_method` (or structured `details`) column, not a silent permanent convention.

## Part B — Contracts

### ADRs
**ADR-003 — Credential-grant command as cloud-recorded intent** (new, `docs/architecture/adr/ADR-003-credential-grant-command-contract.md`). Trigger: this is the first device/panel-command event contract in the system (AGENTS.md's "physical actions are async idempotent commands" rule, previously prose-only) and it establishes the reusable command envelope (`tenant_id`, `correlation_id`, `idempotency_key`, `expiry`, reserved-nullable `site_id`/`device_id`) that later badge-print/door-release commands will reuse verbatim — the same kind of "this becomes the pattern" decision ADR-001/ADR-002 were for tenancy/outbox. Given that "reused verbatim" framing, the canonical envelope does **not** include a `zone` field: `.claude/rules/contracts.md` defines the envelope as tenant/site/device/correlation-id/expiry/idempotency-key, and `site_id`/`device_id` (already reserved-nullable on `outbox_messages`) are the correct — if currently both-null — place to express targeting. Zone-scoping stays out of the frozen envelope entirely until a real zone-configuration story defines it, rather than baking a throwaway `"site-default"` string into a contract every future device command inherits.

ADR-003 also explicitly records, as open questions rather than settled design: (a) the `expiry` field is a known-wrong placeholder (reuses the check-in code's arrival deadline, not a real visit-duration/credential-validity policy — no such field exists yet); (b) this story amends `visit-lifecycle.yaml` itself (the `side_effects` addition below), which per `.claude/rules/contracts.md` requires a contract ticket + owner approval from each consuming component — web, kiosk, core, edge — so ADR-003 names all four and records that edge-connector sign-off is required even though `apps/edge-connector` is still a README scaffold; (c) `credential_grant_command` is wired as a side effect of only the `checkin_verified` entry to `CheckedIn` in this story, not the other three entry transitions (walk-in, dual sign-off, hold-release) — flagged so a later story doesn't silently grant check-in without a credential command.

Security posture: both new outbox message payloads (credential-grant and arrival-notify) are envelope-encrypted, uniformly with the existing `visit.checkin_code.dispatch` precedent — see Event contracts below; this removes an earlier draft's "the credential-grant payload doesn't need encryption since it carries no PII" idea, which turned out to be unbuildable against `outbox_messages.payload_key_ref`'s `NOT NULL` constraint and would have diverged from ADR-002 §5's "never cleartext" invariant without amending it. Encrypting a no-PII payload costs nothing and keeps the table's encryption invariant uniform rather than needing a plaintext/ciphertext discriminator column.

### Statemachine impact (`packages/contracts/statemachine/visit-lifecycle.yaml`)
- No new states. Amend the existing `checkin_verified` transition (`Registered -> CheckedIn`) to add `side_effects: [credential_grant_command]`, symmetric with the `credential_deprovision_command` side effect already declared on `CheckedIn -> CheckedOut`/`CheckedIn -> Denied`. This is the only structural change to the contract file.
- `app/domain/visits/state_machine.py`: add `("Registered", "checkin_verified"): "CheckedIn"` to the frozen transition table (the only new row this story adds).

### API contract delta (`packages/contracts/openapi/visits.yaml`)
- New `POST /visits/checkin`: request `{ checkin_code: string }`; `200` → `Visit` (now `CheckedIn`); `403` → caller lacks `checkin_visits`; `404` → uniform "invalid or expired check-in code" covering unknown/wrong-tenant/expired/already-consumed (anti-enumeration, same principle as US-11's portal errors — never distinguish these).
- `Visit` schema gains `checked_in_at` (nullable datetime).

### Event contracts (new)
- `packages/contracts/asyncapi/credential-grant-command.yaml` — published to `outbox_messages` (message_type `visit.credential_grant.command`) on successful check-in. Fields per `edge-dotnet.md`: `tenant_id`, `correlation_id`, `idempotency_key` (deterministic: `sha256("visit.credential_grant.command:" + visit_id)`), `expiry` (= `checkin_code_expires_at` — a known-wrong placeholder per Part A's Risks, flagged as an ADR-003 open question, not a settled design), `site_id`/`device_id` (`null`, reserved — no zone/site schema exists yet; no `zone` field in the canonical envelope, per the ADR-003 note above). **Payload IS envelope-encrypted**, uniformly with every other `outbox_messages` row (ADR-002 §5) — even though this payload carries only opaque UUIDs and no visitor PII, encrypting it costs nothing and avoids needing a plaintext/ciphertext discriminator on a table whose invariant is "payload is always ciphertext."
- `packages/contracts/asyncapi/visit-arrival-notify.yaml` — published alongside it (message_type `visit.arrival.notify`) for the host-notification intent. Payload: `tenant_id`, `visit_id`, `correlation_id`, `idempotency_key` (`sha256("visit.arrival.notify:" + visit_id)`), `host_user_id`, `host_email` (from `users.email` — PII), `visitor_full_name`, `tracking_reference`. Envelope-encrypted, same as `visit-checkin-dispatch`. Delivery (actual email/WhatsApp send) remains the not-yet-built relay worker's job, per US-11's precedent. This message type must be added to the same standing PII-retention/purge GA gate US-11 already tracks for `visit.checkin_code.dispatch` (undispatched/failed-row purge window) — not assumed covered by virtue of reusing the same table; this is a new PII-bearing thing to register per `database-postgresql.md`'s "retention/purge jobs must cover every new store added."

### RBAC delta (additive, bumps policy version to `v3`)
New permission `checkin_visits`, granted to `reception_security` and `tenant_admin` (same two roles `view_visits` was granted to in US-11) — **not** `host`: check-in is a reception/security action in this staff-operated interim UI, not a host decision, so no host-ownership check applies here (unlike `approve`/`deny`).

### Gherkin scenarios
```gherkin
Feature: Pre-registered QR check-in (US-01, hardware-free)

  Scenario: Valid QR check-in transitions Registered to CheckedIn
    Given a visit "V1" in tenant "acme" is Registered with an unexpired check-in code
    And I am authenticated in tenant "acme" with the checkin_visits permission
    When I submit that check-in code to POST /visits/checkin
    Then the response is 200 with status CheckedIn
    And a visit.credential_grant.command outbox row exists for "V1"
    And a visit.arrival.notify outbox row exists for "V1"
    And a visit.checked_in audit event exists with verification_method "qr"

  Scenario: Expired check-in code is rejected uniformly
    Given a visit "V2" in tenant "acme" is Registered with a check-in code that expired yesterday
    And I am authenticated in tenant "acme" with the checkin_visits permission
    When I submit that check-in code to POST /visits/checkin
    Then the response is 404 "invalid or expired check-in code"
    And "V2" remains Registered

  Scenario: A code from another tenant is rejected with the same uniform error
    Given a visit "V3" in tenant "globex" is Registered with a valid check-in code
    And I am authenticated in tenant "acme" with the checkin_visits permission
    When I submit V3's check-in code to POST /visits/checkin
    Then the response is 404 "invalid or expired check-in code"
    And no information distinguishes this from an unknown or expired code

  Scenario: A caller without checkin_visits is forbidden
    Given a visit "V4" in tenant "acme" is Registered with a valid check-in code
    And I am authenticated in tenant "acme" as a host with no checkin_visits permission
    When I submit that check-in code to POST /visits/checkin
    Then the response is 403
```

## Part C — Plan

### Definition of done
- All 4 Gherkin scenarios pass as executable tests.
- `checkin_verified` is the only new row in `state_machine.py`'s transition table; every other `(status, trigger)` pair still raises `InvalidTransitionError` (regression-tested).
- The guarded `UPDATE ... WHERE status='Registered' AND checkin_code_hash=:hash AND tenant_id=:tenant_id AND checkin_code_expires_at > :now` is proven race-safe (concurrent double-submit of the same code → exactly one 200, the other 404) and proven single-use (a second submission of an already-`CheckedIn` visit's code → 404, not a second transition). Expiry is folded into this single `WHERE` clause, not checked as a separate step after the UPDATE — a test asserts an expired-but-real code and an unknown/wrong-tenant code produce identical behavior (zero rows matched, no status flip, no rollback needed), closing the timing/behavior oracle a two-step check would create.
- `within_visit_window` is enforced from the new persisted `visits.checkin_code_expires_at` column only — a test asserts the domain check never queries `outbox_messages`. A `NULL` value fails closed by construction (`NULL > :now` is never true in SQL) — directly tested.
- `watchlist_clear` stub is a named function (not an inline literal), covered by a test asserting it is called and returns `True`, with a comment pointing at this plan's Risks section. A test also asserts no field or audit event written by this story's code implies a watchlist check was performed/cleared.
- Credential-grant and host-arrival-notify outbox rows are written atomically with the state transition (one DB transaction) — a test asserts a failed transition writes neither.
- **Both** the credential-grant and arrival-notify outbox payloads are envelope-encrypted (uniform with every existing `outbox_messages` row, ADR-002 §5) — a test asserts `payload_key_ref` is populated and `payload` is not valid cleartext JSON for both message types.
- `visit.checked_in` audit event carries `actor` (the authenticated staff principal, i.e. `checked_in_by_user_id`), `correlation_id`, and `reason="qr"` (the coded stand-in for the contract's `verification_method` field, following the existing coded-`reason` convention, documented in ADR-003 as audit-schema debt) — all three asserted directly, not just "an audit row exists."
- Cross-tenant check-in attempt is directly tested two ways: (1) Scenario 3 — a legitimately-authenticated `acme` principal submitting `globex`'s code → uniform 404; (2) a forged-token/attacker-chosen-`tid` test against `POST /visits/checkin` specifically (the US-01-specific version of the pattern US-11 required for its own routes — not assumed inherited).
- `visit.arrival.notify` is registered under the same standing PII-retention/purge gate US-11 already tracks for `visit.checkin_code.dispatch` — confirmed, not assumed, since it's a new PII-bearing message type even though it reuses the existing table.
- `0003_visit_checkin` migration has a tested `downgrade()`; new columns and the `checkin_visits` seed roll back cleanly; `/confirm-schema` passes.
- No secrets, PII, or the plaintext check-in code appear in any log call site in this story's new code; `VisitOut`/the check-in response never echoes `checkin_code_hash` or the submitted plaintext code.

### User journey (demo path)
1. A visit "V1" already exists in `Registered` status with a valid check-in code (produced by US-11's `approve_visit` flow, now also persisting `checkin_code_expires_at`).
2. A `reception_security` staff member signs in to `apps/web` (existing MSAL flow), sees the new `/checkin` page (permission-gated).
3. They enter/paste the check-in code and submit → `POST /visits/checkin` → `200`, visit shows `CheckedIn`.
4. A `visit.credential_grant.command` outbox row and a `visit.arrival.notify` outbox row now exist for V1; a `visit.checked_in` audit event is recorded with `reason="qr"`.
5. Resubmitting the same code → `404` "invalid or expired check-in code" (already consumed).
6. A `globex`-tenant staff member submitting V1's code → same `404`, no distinguishing information.
7. A `host`-role user (no `checkin_visits`) attempting the same call → `403`.

11. **`/confirm-schema` final pass** across the three new `visits` columns and the `checkin_visits` seed, before `/verify-story`.

## Three questions

**1. What was the hardest decision in this plan?**
Whether to implement `watchlist_clear` as a real check or a stub, and — having decided a stub is the only honest option this early (no watchlist data source exists anywhere in the system yet) — how to make that stub impossible to miss later. A silently-`True` guard buried inline in a conditional would be indistinguishable from a real check to anyone reading the call site; naming it as its own function, commenting it, and repeating the flag in this plan's Risks section (and requiring `/document-story` and `/release-readiness` to re-surface it) is a heavier process cost than just writing `True`, but the alternative is a security control that only *looks* implemented.

**2. What alternatives were rejected, and why?**
- **Building the Flutter kiosk QR-scan screen now**: rejected — this wave is explicitly hardware-free; a staff-operated web page achieves the same demo value (prove the state transition + side effects work end-to-end) at zero device/camera-SDK cost, and the real kiosk screen is better built once it can also carry the face-verification path in one pass rather than twice.
- **Host-ownership check on `POST /visits/checkin`** (mirroring `approve`/`deny`'s `host_user_id` match): rejected — check-in is a reception/security action operating on behalf of an arriving visitor, not a host decision; forcing a host-ownership check here would model a self-service kiosk flow that doesn't exist yet, not this story's staff-operated interim UI.
- **Distinguishable error codes for expired vs. wrong-tenant vs. already-consumed vs. unknown code**: rejected in favor of one uniform 404, extending the exact anti-enumeration reasoning US-11's review already established for the portal endpoints — a more precise error would leak validity information to whichever principal calls this endpoint, staff or not.
- **Nulling `checkin_code_hash` on successful check-in** to force single-use explicitly: rejected — the guarded `WHERE status='Registered'` condition already makes replay impossible by construction (US-11's established idiom), and nulling the hash would only remove a value that's otherwise harmless to retain (it's a one-way hash, not the plaintext) while adding no additional guarantee.
- **A real `sites`/`zones` schema for the credential-grant command's zone scoping**: rejected — no story in Wave 1 builds multi-site administration (PRD 3.10); inventing a real zones table now would be speculative design ahead of the story that actually needs it. The placeholder string plus the already-reserved-nullable `site_id`/`device_id` columns keep the command's shape forward-compatible without guessing the real model.

**3. What's the least confident part of this plan?**
Whether "host notified < 10s" is adequately satisfied by outbox-write latency alone, given the actual delivery (relay) worker still doesn't exist. US-11 already made this exact scope cut once for the visitor-facing check-in-code dispatch; this plan repeats it for the host-arrival notification. Repeating the same deferral a second time without the relay-worker story having landed yet is the part of this plan most likely to need a human call: either accept the cut again, or treat "build the relay worker" as a prerequisite this wave is implicitly depending on twice over.

## Design-gate review disposition

Two independent cold reads (domain-architect; security-privacy-reviewer) ran against the initial draft before Gate 1. Both, independently, found the same Blocking defect: the draft proposed leaving the credential-grant outbox payload unencrypted, which cannot actually be built against `outbox_messages.payload_key_ref`'s `NOT NULL` constraint and would have diverged from ADR-002 §5's "payload is always ciphertext" invariant without amending it. **Resolved** in this revision: both new payload types are envelope-encrypted, uniformly with every existing outbox row — no schema change needed, no discriminator column, no ADR-002 amendment.

Both reviewers' Should-fix items are folded into Part A's Risks, Part B's ADR-003 scope, the Definition of Done, and the numbered tasks above: the zone-placeholder now stays out of the canonical device-command envelope; the expiry check is folded into the guarded `UPDATE`'s `WHERE` clause (closing a timing/behavior oracle domain-architect and security-privacy-reviewer both independently flagged from different angles); the `within_visit_window`/credential-`expiry` conflations and the `verification_method`-as-`reason` overload are now named explicitly as interim placeholders/audit debt rather than settled design; a forged-token cross-tenant test is added alongside the wrong-tenant-code scenario; the watchlist stub's scope now explicitly covers both the guard-stub itself and the unwired `Registered -> Held` edge; and retention/purge coverage for the new PII-bearing `visit.arrival.notify` message type is an explicit task rather than assumed.

Full reviewer reports are not persisted as separate files at this stage (pre-Gate-1 cold read, not a post-implementation `/verify-story` pass) — this section is the record of what they found and how this plan responds.
